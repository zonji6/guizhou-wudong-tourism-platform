# 贵州乌冬文旅“衣食住行”综合服务平台开发文档

**版本：** 1.0
**运行方式：** 本机答辩演示
**原则：** 业务服务确定、AI 编排可控、知识来源可追溯、运行轨迹可观察。

## 1. 总体架构

~~~text
原生微信小程序 / Vue PC 门户 / Vue 管理后台
                  │
        Java Spring Boot 文旅服务
  资源、社区、知识原文、预约订单、后台管理
                  │
        Python FastAPI AI 服务
  LangGraph、DeepSeek、RAG、WebSocket、LangSmith
                  │
       MySQL                 Redis Stack
  业务事实与原文        向量检索与短时状态
~~~

## 2. 技术选型

| 技术 | 职责 |
| --- | --- |
| 原生微信小程序 | 移动游客端：资源、AI、预约、订单、社区 |
| Vue 3 + Vite | PC 文旅门户与 Web 管理后台 |
| Java Spring Boot | 资源、内容、订单、MySQL 事务和后台接口 |
| Python FastAPI | WebSocket、LangGraph、RAG、模型调用 |
| LangGraph StateGraph | 快慢车道、节点编排、状态和错误回退 |
| DeepSeek | 意图理解、路线生成、结构化卡片 |
| 百炼 text-embedding-v4 | 贵州乌冬知识文本向量化 |
| MySQL 8 | 商家、服务、社区、订单、知识原文和索引状态 |
| Redis Stack | 向量检索、短时会话和任务状态 |
| LangSmith | 开发期 Trace |

## 3. 服务边界

### Java 文旅服务

Java 是 MySQL 业务事实唯一写入口，负责商家、服务、社区、知识原文、预约订单和后台接口。Java 提供受控内部工具给 Python 调用。

Java 不负责 Prompt、模型调用、向量化和 LangGraph。

### Python AI 服务

Python 负责 WebSocket、LangGraph、DeepSeek、RAG 和卡片生成；通过 HTTP 调用 Java 内部工具。Python 不直接写入商家、订单和社区等业务表。

| 数据 | 唯一事实来源 | 访问方式 |
| --- | --- | --- |
| 商家、服务、订单、社区、知识原文 | MySQL | Java 读写；Python 经 Java 工具读取 |
| 向量、检索元数据、短时会话 | Redis Stack | Python 索引与检索 |
| Trace | LangSmith | 开发期追踪；后台只保留脱敏摘要 |

## 4. LangGraph 设计

每个会话带稳定的 thread_id。状态包含用户输入、页面动作、意图、日期/人数/预算/偏好、检索结果、工具结果、待确认预约、最终卡片、任务事件和错误信息。

~~~text
START → route
route ── 页面动作 ──→ service_search → compose_card → END
route ── 自由文本 ──→ intent
intent ── 信息不足 ──→ clarify → END
intent ── 行程规划 ──→ retrieve → itinerary → compose_card → END
intent ── 知识问答 ──→ retrieve → answer → compose_card → END
intent ── 预约协助 ──→ service_search → pending_booking → compose_card → END
~~~

- 快车道处理明确的页面动作，不调用模型。
- 慢车道处理复杂自然语言。
- 模型输出先经 Pydantic 校验。
- 仅允许行程、资源推荐、知识回答、补充问题、待确认预约、错误六种卡片。

首个固定验收输入为“我想体验贵州乌冬的苗族文化和茶旅”。此输入默认路由到行程规划，缺少日期、人数或偏好时先返回补充问题；信息齐全后，行程卡片按“茶园体验、制茶/品茶、苗寨文化、餐饮或民宿承接”的顺序组合 Java 服务返回的真实演示资源。

## 5. RAG 知识库

~~~text
后台发布攻略/文化/服务资料
→ Java 保存 MySQL 原文
→ 调用 Python 索引接口
→ 文本切块
→ 百炼向量化
→ Redis Stack 建立向量索引
→ AI 检索 Top-K 内容
→ DeepSeek 基于来源生成答案
~~~

- 切块约 500 个中文字符，重叠约 80 个字符。
- 向量模型为 text-embedding-v4，维度为 1024。
- 每次检索最多返回 4 个带来源的块。
- 无检索结果时明确提示，不生成事实性答案。
- 本期不实现重排序、多模态检索或托管知识库。

## 6. 接口约定

### Java 公共 API

~~~text
GET  /api/services?category=stay|food|travel|culture
GET  /api/services/{id}
GET  /api/posts
GET  /api/knowledge-documents
POST /api/admin/knowledge-documents
POST /api/bookings
POST /api/bookings/{id}/confirm
GET  /api/bookings/{id}
~~~

### Java 内部工具 API

~~~text
GET  /internal/agent/services/search?keywords=&tags=
POST /internal/agent/pending-bookings
GET  /internal/agent/bookings/{id}
~~~

内部 Agent 只能创建待确认预约；用户通过游客端确认后，Java 才能把订单转为已确认。

### WebSocket

Python 提供 WS /ws/assistant。事件顺序为：

~~~text
task_started → node_started → tool_finished → card_ready → completed
~~~

失败时发送 failed 与安全错误卡片。前端只显示任务进度，不显示模型原始思维链。

## 7. 本机配置与启动

### 环境要求

Java 21、Maven、Node.js 20+、Python 3.11+、Docker Desktop、微信开发者工具、DeepSeek API Key，以及后续创建的百炼与 LangSmith Key。

### 环境变量

~~~dotenv
DEEPSEEK_API_KEY=
DASHSCOPE_API_KEY=
LANGSMITH_TRACING=false
LANGSMITH_API_KEY=
LANGSMITH_PROJECT=udong-tourism-demo
JAVA_SERVICE_BASE_URL=http://127.0.0.1:8080
~~~

Key 只保存在本机环境文件，不得写入 Git、小程序源码、截图或答辩文档。

### 启动方式

Docker Compose 仅启动 MySQL 与 Redis Stack。Java、Python 和 Vue 使用本机进程运行，便于定位故障。

~~~powershell
docker compose -f infra/docker-compose.yml up -d
powershell -ExecutionPolicy Bypass -File scripts/start-demo.ps1
~~~

微信开发者工具本机联调时关闭本地调试域名校验；本期不支持真机公网访问。

## 8. 验证与降级

自动验证保留：

1. Agent 卡片仅允许白名单类型。
2. 预约确认后订单可查询为 CONFIRMED。
3. 快车道返回确定性资源卡片。
4. RAG 切块保留来源；未检索到资料时不生成事实性答案。
5. 最终卡片前至少发送一个进度事件。

答辩前人工前向验收：

~~~text
PC 浏览资源和社区
→ 小程序提出“我想体验贵州乌冬的苗族文化和茶旅”
→ 查看进度、来源与推荐
→ 确认预约
→ 后台更新订单
→ 后台查看脱敏 AI 轨迹
→ 已配置 LangSmith 时查看同一次会话 Trace
~~~

| 故障 | 用户可见处理 | 不受影响部分 |
| --- | --- | --- |
| DeepSeek 不可用 | AI 服务暂不可用 | 资源、社区、订单、后台 |
| 百炼未配置或索引失败 | 知识库未配置或资料暂不可用 | 快车道、订单 |
| Redis 不可用 | AI 问答和规划降级提示 | Java 业务服务 |
| LangSmith 未配置 | 不上传 Trace，后台仍有本地摘要 | 全部业务 |
| Java 工具失败 | AI 返回错误卡片，不编造数据 | 已有订单与内容 |

## 9. 前端视觉约束

- 设计令牌以茶绿、靛蓝、米白、暖铜色为主；正文与操作区必须保持足够对比度。
- 首屏和资源详情优先展示真实贵州乌冬山林、村寨、茶旅、民宿和在地体验图片。
- 苗族纹样只作为低频装饰，不作为大面积背景，也不在信息密集区重复使用。
- 游客端以大图、清晰分类卡片和明确预约按钮建立温暖的旅行感；管理后台保持简洁中性，以数据与操作效率为主。
- AI 助手卡片使用统一的白底信息卡结构，来源、价格、预约状态和错误提示必须可读，不可用纹样替代文字信息。
