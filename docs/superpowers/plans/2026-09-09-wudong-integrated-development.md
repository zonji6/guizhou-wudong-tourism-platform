## 3. 资料进入系统的流程

### 3.1 先保留来源，再生成演示目录

不把 136 MB Word 原件或 228 个原始媒体文件放入 `web/public`。当前完整提取、图片关系与结构化草稿在被 Git 忽略的 `tmp/source-review/content/`；原件仍留用户原路径。可提交的版本是去除联系方式和原图的映射规则、来源定位与问题清单，发布资产另行选择。

后续离线工具建议固定为 `scripts/content/prepare_wudong_catalog.py`，读取已有 `source-blocks.json`、截图转录及 `content-catalog-draft.json`，生成 `data/content/wudong-candidates.json` 与 `data/content/wudong-source-index.json`。导入工具 `scripts/content/import_wudong_catalog.py` 默认只输出数量和冲突；显式本机演示导入时才写入。工具不是游客上传接口，也不让 AI 自行读 Word 后直接改业务库。

候选记录最小形状：

```json
{

  "entityType": "ROOM_TYPE",
  "name": "大床房",
  "parentSourceKey": "wudong-docx-20260909:P0062",
  "referencePrice": { "amount": "147.00", "currency": "CNY", "unit": null },
  "demoPrice": null,
  "referenceCapacity": null,
  "demoCapacity": null,
  "simulationNote": null,
  "rawBedDescription": "1张1.51米大床",
  "verificationStatus": "UNVERIFIED",
  "demoData": true,
  "publicationStatus": "DRAFT",
  "issues": ["计价单位和入住日期未写明", "床宽需要核对"],

```

金额保留十进制字符串；原始缺失值为 `null` 而不是零。用户已允许为本机演示补充模拟值：价格、容量等分别放在模拟字段，注明计价单位、容量适用范围和模拟口径，不覆盖 `referencePrice`、原始容量或截图冲突；示例中的 `demoPrice`、`demoCapacity` 与 `simulationNote` 在造样例时填写。原始来源 ID 与公开业务 UUID 分离，前端不接触电脑路径。`sourceKey` 唯一保证重跑不重复导入；后台已编辑记录不被二次导入静默覆盖，变更进入差异清单。

建议在现有目录实体增加 `sourceKey`、`verificationStatus`、`priceNote`、`updatedAt`，图片记录 `sourceAsset`、`usageScope`、`caption`、`focalPoint`；原始参考与模拟值采用分列语义。这属于下一轮数据模型细化，不是本轮数据库变更。联系方式留在受控本机资料中，仅已确认可公开的商家联系方式允许进入公开接口；不伪造真人联系方式或素材权利许可。模拟样例不能包装为真实商家报价、容量或库存，公开可售仍未授权。

### 3.3 RAG 与 MySQL 的分工

MySQL 是商品、商家、房型、订单、价格和发布状态的事实来源。AI 对可订性和资源是否存在的判断必须查询 Java，不能从向量片段猜测。RAG 放文化解释、地点故事、工艺说明、带来源的到访提醒和社区路线经验。

文本按一个完整主题切块，保留标题/原文定位/地域尺度/来源时间/核验状态；表格按“商家 + 一条房型或餐食”保留上下文，不能截断后丢失所属商家。手机号、内部路径、批发采购信息和未授权材料不进入公开知识索引。

索引版本包含 `contentHash + embeddingModel + dimension`。文档或模型变化重建对应版本，不把不同维度混入同一索引。召回结果只保留已发布公开资料，模型回答附来源标题；没有足够证据就说明未知，跨地区材料明确其地域，不能改写成乌东独有。

## 4. 需要先锁定的 API 细节

以下是下一阶段契约建议，继承现有 Web 字段。写入 `tourism-api-v2.md` 后，各端按同一版本实施，避免继续 v1/v2 各跑一半。

### 4.1 游客目录与提交

沿用 `GET /api/products`、`/api/foods`、`/api/stays` 及各自详情；餐食支持按 `merchantId` 读取同店菜单，补全 Web 已用的 `GET /api/room-types/{id}`。公开目录仅返回已发布且未归档记录，列表继续直接返回数组以兼容现有 `tourismApi.js`，不要突然改成 `{items:[]}`。

| POST 路径 | 前端请求字段 | 服务端初态 |
| --- | --- | --- |
| `/api/product-orders` | `productId, quantity, pickupPoint, contactName, contactPhone, note, sourceThreadId` | `PENDING_PICKUP` |
| `/api/food-orders` | `merchantId, items:[{foodItemId, quantity}], visitAt, peopleCount, contactName, contactPhone, note, sourceThreadId` | `PENDING_VISIT` |
| `/api/stay-bookings` | `roomTypeId, checkInDate, checkOutDate, roomCount, peopleCount, contactName, contactPhone, note, sourceThreadId` | `PENDING_CONFIRMATION` |

三类返回各自 `id`、对应字段、状态、`demoData`、`createdAt`、`updatedAt`。商品和住宿返回目标 ID 与名称快照，商品另含 `pickupPoint`，住宿目标是房型，不混成住宿主体。餐食返回店铺归属、整单共享信息、全部明细与合计快照，不能继续以单个 `foodItemId` 表示整单。价格/演示状态/取货点须由 Java 重新核对，客户端值不作可信事实。`sourceThreadId` 可空，只作来源关联，不授予读取其他订单的权限。

餐食以 `merchant` 为店铺归属，同店菜单可多选菜品、饮品、套餐并调整份数，店内选餐篮汇总成一张到店订单，不做跨店购物车。`food_order` 主单只属于一家店，到店时间、人数、联系人与备注整单共享；`food_order_item` 保存每项名称、单位、模拟单价、数量和行金额快照，主单保存合计。Java 校验 `items` 非空、份数为正整数、全部条目属于请求的店铺且已上架，混店整单拒绝；服务端按明确模拟单价计算行金额与合计，不信任客户端报价，主单与全部明细在同一事务写入，不能部分成功。确认页、我的订单和后台均展示单店整单与明细，历史金额读取订单快照。

本机匿名 UUID 由 `X-Visitor-Id` 传递。Java 校验格式并限定 `/api/me/product-orders`、`/api/me/food-orders`、`/api/me/stay-bookings` 的归属；任何按 ID 的读取同样检查归属。该 UUID 是本机演示凭据，不是生产登录认证，不提供手机号查单。

`visitAt` 当前前端发送本地日期时间字符串，契约固定按 `Asia/Shanghai` 解释，响应仍用同一字段语义；`checkInDate`、`checkOutDate` 均为 `YYYY-MM-DD`，离店日期必须晚于入住日期。联系人 1～80 字符，电话 1～32 字符，备注最多 500 字；数量、房间数 `roomCount`、人数 `peopleCount` 为正整数。住宿夜数由两个日期计算，不接受客户端任意夜数；容量校验按明确的每间房容量与房间数计算，模拟容量须保持标识，不能当成真实核验结果。未知容量可单列模拟值以支持本机提交，不必等商家确认后才造样例。前端和 Java 都处理这些字段，数据库不依赖前端校验。

住宿仍由后台确认，不做实时房态、动态价格或库存锁定。仅在明确模拟计价口径时演示金额；例如模拟单价明确为“元/间/晚”时，按单价 × 夜数 × 房间数计算，并显示模拟说明。原始参考报价缺少单位时不直接参加该计算，也不承诺真实应付金额。

提交过程禁用重复按钮；下一阶段建议增加请求幂等键，网络不确定时保留同一键重试，返回原订单而不是重复创建。取消创建中请求不能撤销已经完成的数据库写入，需提示用户去我的订单核对。

### 4.2 状态转换建议

```text
商品：PENDING_PICKUP → PICKED_UP 或 CANCELLED
餐食：PENDING_VISIT → COMPLETED 或 CANCELLED
住宿：PENDING_CONFIRMATION → CONFIRMED 或 CANCELLED
      CONFIRMED → COMPLETED 或 CANCELLED
```

完成与取消均为终态。餐食状态作用于整张到店订单，不设置逐菜状态，也不新增支付、配送、退款或实时库存。后端同时检查当前状态、目标状态与类型，不能只验证目标字符串合法。建议更新带 `expectedStatus`，条件更新未命中返回冲突并要求刷新；没有支付的取消不产生退款记录。旧 `Booking.PROCESSING` 不传播到新领域状态机。

### 4.3 社区与行

统一 `GET /api/posts?type=NORMAL|ROUTE_GUIDE&tag=...`，响应类型字段为 `postType`。发布请求为 `content, tags, postType`，路线攻略追加 `title, routeNodes`；节点包含 `order, placeId, note`。公开节点引用存在的地点 ID；未知地点只保留为正文，不伪造 ID。作者展示名由 Java 生成，用户不能冒充运营或商户身份。

建议正文限 2,000 字、标题 80 字、最多 5 个标签/每个 20 字、路线最多 12 节点。前端输出纯文本，不渲染用户 HTML。行页只引用同一篇 `ROUTE_GUIDE`，不生成另一套攻略记录。我的“行程”展示保存的规划结果，不是第四类交易订单。

行页当前先提供水彩虚拟示意地图，依据既有资料和可找到的信息选取固定地点节点，以独立的相对坐标 `(x, y)` 与连线展示路线顺序；节点布局数据不复制社区攻略内容。地图与路线卡清楚标明“虚拟示意地图，非等比例”，真实经纬度未知时为空，不从手绘图或示意位置反推。不得显示精准里程/时长或声称实时导航、班次、道路状态；地点列表辅助展示，真实地图在授权与配置齐备后接入。

### 4.4 AI 提案与内部接口

用户已确认产品行为：AI 订餐/住宿方案保存为草稿，与正式订单分开，离开后可从“我的”找回并继续修改；用户确认提交才生成正式订单。需要能按当前访客列出和读取草稿，不能只留一张无法找回的聊天卡片。以下存储候选仍待技术讨论，不把草稿功能确认等同于已选定检查点、Java 表结构或接口方案；保存触发、提交后的草稿处理、保留期限也尚未锁定。

当前前端使用严格校验的 `cardVersion=2.0`；下一阶段加入餐食 `merchantId/items` 和住宿四字段时，必须先锁定新的卡片/提案协议版本，同步 Java 内部契约、Python 发送端与 Web/小程序解析器，不能只给 2.0 增加键，本轮不修改现行协议文件。AI 餐食/住宿结果是 `proposal`；建议保存在线程检查点，或由 Java 保存为独立短期提案记录，与正式三类订单集合隔离。存储方案仍需与用户讨论后锁定，本轮未在两者之间作选择，不能继续以旧通用 booking 当作提案。

下一版本餐食提案使用 `merchantId, items:[{foodItemId, quantity}], visitAt, peopleCount`，一份提案只包含同店已上架条目与正整数份数，不再以单一 `targetId` 表示整单。住宿提案使用 `targetType, targetId, targetName, checkInDate, checkOutDate, roomCount, peopleCount`，其中 `STAY` 的 `targetId` 是房型 ID，不是住宿主体 ID。公共字段建议为 `proposalType, note, sourceThreadId, requiresVisitorConfirmation=true, demoData`，各类型的字段集合与空值规则随新协议一起明确。住宿必须遵守日期先后、正整数和由日期计算夜数的规则，不凭不完整提案伪造字段齐备。提案备注按现有解析器限制为 300 字，正式订单备注允许 500 字。`visitAt` 统一上海本地日期时间；若上游返回带时区值，须先换算到上海时间再预填 `datetime-local`，不能直接删掉时区后缀。提案不含联系人或正式订单状态。用户点击后重新读 Java 目标详情；餐食重新核对店铺、全部菜单条目及当前模拟单价，预填整单确认页，核对联系人，再由游客提交正式订单。商品只有推荐与详情跳转，不生成提案。

内部查询与提案操作必须绑定由服务层确认的访客/线程关系；不能直接相信模型给出的 visitorId 或 sourceThreadId。Python 不能写目录、发布社区或更新订单状态。旧 `LEGACY_*` 动作只能在明确的旧演示模式中出现，不自动穿透到新订单。

## 5. AI 与运行时设计

### 5.1 保持选型，补齐实际能力

当前 Compose 已使用 Redis Stack；建议用维护方提供的 Redis checkpointer 适配器接入 LangGraph，复用 Redis，而非为检查点再引第三个数据库。该适配器需要 RedisJSON 与 RediSearch，不能认为任意普通 Redis 都兼容；实施时锁定与现有 LangGraph/redis 库兼容的版本，并配置持久卷与持久化。参考 [Redis 适配器安装要求](https://redis-developer.github.io/langgraph-redis/main/user_guide/installation.html)。

线程使用 LangGraph 的 `thread_id` 关联检查点，但访问控制仍由 Java/Python 校验访客归属。它提供恢复上下文的机制，不等于已实现断线续传；恢复失败应明确提示，不伪造“记得上一轮”。参考 [LangGraph 持久化说明](https://docs.langchain.com/oss/python/langgraph/persistence)。

云 Embedding 到位前保留标为 `keyword_demo` 的关键词检索。到位后补 `baseUrl`、`model`、`dimension`、输入长度与鉴权配置，校验响应维度和有限数值；索引与查询使用同一模型和维度。超时/限流明确降级，不把随机向量当成功结果。

DeepSeek 负责语义理解与内容组织，不承担库存、价格、坐标和订单状态事实判断。固定“看商品/订单”等页面动作直接查询 Java，不必额外调用模型。

### 5.2 WebSocket 与观测

保留现有事件封装并统一 v2 payload。当前两端 `assistantProtocol.js` 使用严格字段集合校验，不能直接向 2.0 事件增加键。若下一阶段采用 `runId` 和递增序号，必须先锁定新的事件契约版本，再同步升级 Web 与小程序解析器及 Python 发送端；未升级前沿用当前封装与请求隔离。旧运行迟到事件不能覆盖新运行结果。阶段事件面向游客显示“理解需求、查找资料、组织建议”等摘要，不透传完整 prompt、工具参数或思维链。

LangSmith 只接脱敏观测数据；默认不上传联系人、访客凭据、原始 Word 或商户私密资料。云追踪是否启用由本机配置决定，失败不阻塞游客业务。后台展示真实运行摘要的时间、节点类别、来源标题、耗时与结果；没有数据则显示暂无记录，不用静态数字冒充真实统计。

### 5.3 本机演示边界

保持回环监听，预览不等于公开部署。后台按店铺维护菜单和筛选餐食订单，本期仍由集中运营使用，店铺归属不扩展为商家账号、登录或权限体系。现有后台没有生产角色权限，匿名 UUID 也不是账号体系；本机仍需限制内部工具访问、保持服务端秘密不进入浏览器。`VITE_*` 会进入客户端，不能存服务端密钥。地图 SDK 如需要可公开且受域名限制的客户端标识，应与服务端秘密分开配置。
