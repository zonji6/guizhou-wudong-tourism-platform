# 贵州乌东后端领域与 AI 服务设计规格

**状态：** 用户已确认（2026-09-09）  
**依赖规格：** `2026-09-09-wudong-five-module-frontend-design.md`  
**目标：** 为已确认的商品、食、住、行、社区、订单、运营后台和乌东向导提供完整且边界清楚的 Java 业务服务与 Python LangGraph AI 服务设计。  
**节奏约定：** “约十小时”仅为阶段性进度检查点，不是范围裁剪依据或完成承诺。所有本规格已确认的功能均为正式范围，按依赖顺序持续实现和汇报。

## 1. 总体边界

```text
Vue / 微信小程序
       │ 公开 REST / WebSocket
       ▼
Java 业务服务 ── 内部受控接口 ── Python LangGraph AI 服务
       │                                  │
       ▼                                  ▼
业务目录、订单、社区、知识            会话检查点、检索、结构化卡片、脱敏轨迹
```

- Java 是商品、餐食、住宿、景点、商家、订单、社区动态和知识资料的业务事实唯一写入口。
- Python 只能通过受控内部接口读取业务资料、查询订单状态，以及为餐食和住宿创建待确认订单；不能写目录、正式订单、订单状态或社区动态。
- 前端所有正式提交均须经过独立确认页。AI 不能代替用户确认或创建正式订单。
- 所有资源、价格、库存、路线、班次、图片、社区内容与 AI 建议在未经核验时都必须保留演示或个人经验标识。

## 2. Java 业务领域

### 2.1 供给目录与商家

运营人员通过后台维护商家及其资料；本期不创建商家账号、登录、提交申请或权限体系。目录使用分领域表，不再将所有内容压入通用资源表：

| 领域 | 最小实体 | 关键字段与关系 |
| --- | --- | --- |
| 商家 | `merchant` | 名称、描述、联系方式、发布状态 |
| 商品 | `product` | 商家、名称、描述、价格、取货点、标签、图片、演示标识、上架状态 |
| 餐食 | `food_item` | 商家、名称、描述、价格、到店时段说明、标签、图片、演示标识、上架状态 |
| 住宿 | `stay_property`、`room_type` | 住宿主体关联商家；房型关联住宿主体，含容量、价格、说明、图片、演示标识、上架状态 |
| 行 | `place` | 名称、类别、描述、经纬度、标签、图片、演示标识、发布状态 |

运营后台具备这些实体的正常新增、查看、编辑、上架/下架或归档能力。物理删除不作为常规运营操作；既有已被订单引用的数据使用下架/归档保留可追溯性。

### 2.2 三类独立订单

商品、餐食和住宿分别建模，避免将数量、取货、到店时间和入住日期混入单一预约表。

| 表 | 创建字段 | 游客状态 | 后台可更新状态 |
| --- | --- | --- | --- |
| `product_order` | `visitor_id`、商品、数量、取货点、联系人 | 待取货 | 已取货、已取消 |
| `food_order` | `visitor_id`、餐食、到店时间、人数、联系人 | 待到店 | 已完成、已取消 |
| `stay_booking` | `visitor_id`、房型、入住日期、人数、联系人 | 待确认 | 已确认、已完成、已取消 |

订单创建前由用户在独立确认页核对字段。商品只支持现场自提；餐食仅为到店餐食/茶点体验；住宿为预约，均不包含真实支付、配送、退款或实时库存/房态。

客户端首次进入生成随机 `visitorId` 并在本机保存；Java 把它写入订单和社区动态。我的订单仅按当前 `visitorId` 读取，禁止通过手机号查单或返回其他访客数据。

### 2.3 社区与路线攻略

`community_post` 扩展为普通动态与路线攻略两种内容类型。动态最小字段包括 `visitor_id`、正文、标签、作者展示名、内容类型、演示标识和发布时间；路线攻略追加标题、节点顺序/摘要与地点引用。

游客可发布文字与标签动态、按标签或内容类型读取动态。没有图片上传、评论、点赞、收藏、举报或审核流。路线攻略属于同一篇社区内容；行模块只引用其卡片作为个人经验，不复制为第二套路线数据，也不标为官方路线。

### 2.4 地点与地图服务

Java 对游客端和 Python 提供地点/景点的已发布资料与坐标，供地图渲染、路线规划和 AI 检索使用。底图、搜索、地理编码、路径计算、实时交通/班次和导航跳转由用户后续选定并提供访问方式的地图服务商承担。

在服务商、地点坐标或数据授权尚未具备时，页面与 API 均须返回明确的演示或未配置状态，不能伪造实时结果。

### 2.5 接口职责

接口按领域分组，具体字段以实现阶段的契约文档为准：

```text
游客端：
GET  /api/products                 GET /api/products/{id}
GET  /api/foods                    GET /api/foods/{id}
GET  /api/stays                    GET /api/stays/{id}
GET  /api/places
GET  /api/posts?type=&tag=
POST /api/posts
POST /api/product-orders           GET /api/me/product-orders
POST /api/food-orders              GET /api/me/food-orders
POST /api/stay-bookings            GET /api/me/stay-bookings

运营端：
/api/admin/merchants
/api/admin/products
/api/admin/foods
/api/admin/stays 与 /api/admin/room-types
/api/admin/places
/api/admin/orders/*/status
/api/admin/knowledge-documents
```

`visitorId` 作为受校验的访客归属凭据随请求传入；响应不得返回其他访客的联系人信息、内部存储路径、密钥、签名 URL、未脱敏错误或不属于当前访客的订单。

## 3. Python LangGraph AI 服务

### 3.1 会话与图结构

同一可见工作台会话重用 `threadId`。LangGraph 持久化检查点保存已确认条件、对话摘要、上一版行程和结构化工具结果；用户补充或修改条件后生成新版本，同时保留上一版供前端标识。服务重启后的恢复能力依赖持久化检查点，不得用前端假状态冒充已理解上下文。

```text
输入
→ 恢复 threadId 状态
→ 固定页面动作？ ──是──→ Java 直接查询 → 卡片
                     │否
                     ▼
                  意图与条件提取
                     ▼
                  缺条件？ ──是──→ 追问卡
                     │否
                     ▼
    目录 / 知识 / 地点 / 社区路线攻略检索
                     ▼
       地图服务可用时补充路线结果；否则如实降级
                     ▼
       行程、知识、推荐或待确认订单卡片
```

固定页面动作（看商品、餐食、住宿、地点或当前访客订单）不调用模型；自然语言请求支持茶旅行程、文化知识、商品/餐食/住宿推荐、景点与路线建议。

### 3.2 工具权限与订单边界

Python 通过 Java 内部接口读取商品、餐食、住宿、地点、知识、已发布社区路线攻略和当前线程关联的订单状态。

- AI 可以为用户已选定、且字段充分的餐食和住宿生成待确认订单；页面仍须在独立确认页提交。
- 商品由用户在详情页选择数量并自行下单；AI 只推荐和跳转，不创建商品订单。
- Python 无权创建正式订单、修改订单状态、写入商家/商品/餐食/住宿/地点资料或发布社区动态。
- AI 不能访问游客间的订单、联系人或非公开资料。

### 3.3 结构化响应、地图与降级

响应卡固定为行程、服务推荐、知识回答、追问、待确认订单和错误。卡片包含公开标题、摘要、明确演示提示、真实服务/地点标识和可公开来源标题；不存在可靠 `serviceId`、地点标识或来源时，不显示对应详情、下单或来源动作。

地图服务商配置有效时，AI 可将路线工具的结果整理成路线卡；未配置或调用失败时，只基于地点和社区路线攻略生成明确标注为演示/个人经验的建议，不能声称有实时导航、班次或道路状态。

### 3.4 脱敏运行摘要

Java 后台展示的 AI 摘要仅含会话标识、节点名、工具类别、来源标题、耗时和最终状态。不得保存或展示提示词、原始思维链、联系人、访问令牌、密钥、内部 URL、SQL、完整工具参数或未处理异常。

## 4. 初始原始资料的开发准备

用户后续提供的商品、餐厅/菜品、住宿/房型、景点与出行资料，属于开发前期的原始数据准备，不属于游客或商家的在线导入功能。

资料交付后，由开发者离线解析、去重、标记来源与核验状态，映射到第 2 节的目录实体，再写成可追溯的演示初始化数据。未核验项在前端持续标注演示数据；不将原始文件、不确定事实或未经授权图片自动公开。

## 5. 实施顺序与进度检查

实现按依赖推进，而非按固定时长删减：

1. Java 迁移、领域模型、目录与匿名访客归属；
2. 三类订单、状态机、游客确认与后台处理；
3. 社区动态/路线攻略、地点资料与后台维护；
4. Python 受控工具、会话检查点、结构化卡片、待确认餐食/住宿订单；
5. 地图服务商配置、已核验地点数据、路线工具和前后端联调；
6. 用户提供原始资料后的离线解析与演示初始化数据写入。

每约十小时只报告已完成、进行中、风险和外部依赖，不把后续项从范围中删除。地图服务商及已核验坐标/资料仍是唯一会影响真实地图与路线结果的外部前置条件。

## 6. 规格自检

- Java 和 Python 写入边界一致：Java 是业务事实唯一写入口；Python 只读及创建受限待确认餐食/住宿订单。
- 三类订单字段、确认入口与状态机与前端规格一致；匿名访客标识避免手机号查单。
- 社区路线攻略只存一份并被行模块引用；不存在第二套路线数据或官方路线暗示。
- 初始原始资料与运行期在线导入已明确区分；前者不新增游客功能或不受控 AI 自动入库。
- 不以十小时为由裁剪已确认功能；地图外部服务商和已核验数据被明确为实施前置条件。
