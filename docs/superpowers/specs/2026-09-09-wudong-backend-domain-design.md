## 1. 总体边界

```text
Vue / 微信小程序
       │ 公开 REST / WebSocket
       ▼
Java 业务服务 ── 内部受控接口 ── Python LangGraph AI 服务
       │                                  │
       ▼                                  ▼
业务目录、订单、社区、知识            会话检查点、检索、结构化卡片、脱敏轨迹
```

- Java 是商品、餐食、住宿、景点、商家、订单、社区动态和知识资料的业务事实唯一写入口。
- Python 只能通过受控内部接口读取业务资料、查询订单状态，以及为餐食和住宿创建待确认订单；不能写目录、正式订单、订单状态或社区动态。
- 前端所有正式提交均须经过独立确认页。AI 不能代替用户确认或创建正式订单。
- 所有资源、价格、库存、路线、班次、图片、社区内容与 AI 建议在未经核验时都必须保留演示或个人经验标识。

## 2. Java 业务领域

### 2.1 供给目录与商家

运营人员通过后台维护商家及其资料；本期不创建商家账号、登录、提交申请或权限体系。目录使用分领域表，不再将所有内容压入通用资源表：

| 领域 | 最小实体 | 关键字段与关系 |
| --- | --- | --- |
| 商家 | `merchant` | 名称、描述、联系方式、发布状态 |
| 商品 | `product` | 商家、名称、描述、价格、取货点、标签、图片、演示标识、上架状态 |
| 餐食 | `food_item` | 商家、名称、描述、价格、到店时段说明、标签、图片、演示标识、上架状态 |
| 住宿 | `stay_property`、`room_type` | 住宿主体关联商家；房型关联住宿主体，含容量、价格、说明、图片、演示标识、上架状态 |
| 行 | `place` | 名称、类别、描述、标签、图片、演示标识、发布状态；真实经纬度与示意节点的相对坐标 `(x, y)` 分离 |

运营后台具备这些实体的正常新增、查看、编辑、上架/下架或归档能力。物理删除不作为常规运营操作；既有已被订单引用的数据使用下架/归档保留可追溯性。

### 2.2 三类独立订单

商品、餐食和住宿分别建模，避免将数量、取货、到店时间和住宿起止日期混入单一预约表。

| 表 | 创建字段 | 游客状态 | 后台可更新状态 |
| --- | --- | --- | --- |
| `product_order` | `visitor_id`、商品、数量、取货点、联系人 | 待取货 | 已取货、已取消 |
| `food_order`、`food_order_item` | 主单：`visitor_id`、店铺、到店时间、人数、联系人；明细：同店多道餐食及各自份数 | 待到店 | 已完成、已取消 |
| `stay_booking` | `visitor_id`、房型、`checkInDate`、`checkOutDate`、`roomCount`、`peopleCount`、联系人 | 待确认 | 已确认、已完成、已取消 |

订单创建前由用户在独立确认页核对字段。商品只支持现场自提；餐食仅为到店餐食/茶点体验；住宿为后台确认预约，均不包含真实支付、配送、退款或实时库存/房态。住宿离店日期必须晚于入住日期，房间数和人数为正整数，夜数由日期计算；仅有明确模拟计价口径时才计算演示金额，不增加动态价格或库存锁定。

餐食采用“一家餐馆、一张主单、多条菜品明细”。`food_order` 保存 `merchant_id`、整单到店时间、人数、联系方式及演示合计；`food_order_item` 保存订单与餐食引用、名称、计价单位、单价、份数和行金额快照，菜单后续改价不改写已提交订单。菜品、饮品和套餐均可作为餐食项；套餐在本期作为一个明细项，不展开成第二套订单。

`POST /api/food-orders` 接收 `merchantId`、`items: [{ foodItemId, quantity }]`、`visitAt`、`peopleCount`、`contactName`、`contactPhone`、`note` 和可选 `sourceThreadId`。Java 校验明细非空、份数与人数为正整数、所有餐食已上架且属于指定店铺；金额依据服务端明确计价单位的模拟单价计算，不信任客户端传入的金额。主单与明细在一个事务中保存，混入其他店铺的餐食则整单拒绝，不自动拆单或部分成功。整单统一完成或取消，不增加逐菜履约状态。

菜单与到店订单均按 `merchantId` 归属，目录支持按店筛选；后台先选店再维护菜单、筛选和处理该店订单，服务端核对所操作资源的店铺归属。本期使用集中运营后台，不把按店管理当成已具备独立商家账号或多租户权限隔离。

旧匿名基线是客户端首次进入生成随机 `visitorId` 并在本机保存，Java 将其写入订单和社区动态。用户已确认 Web 与小程序采用同一套用户名密码及 Spring Security + JWT，共享个人行程、草稿和订单；开放最简自助注册，用户名密码必填、昵称可选，暂不接短信或邮箱验证。公共内容免登录，保存行程或草稿、下单、发社区和查看个人记录须登录；登录后恢复原操作，不自动提交订单。两端独立本地 UUID 不再是最终方案，会话传输与失效细节、凭据结构及旧匿名记录处理继续讨论，本轮不改表或实现登录。读取、修改和取消始终限定当前已确认归属的用户，禁止通过手机号查单、任意指定他人标识或所有游客共用固定演示身份。

用户现已要求运营后台只供开发和运营人员使用，从游客顶栏移除入口、右侧改为“我的”。Java 须对后台读写接口增加管理授权；普通自助注册不能获取该权限，不能只靠前端路由或隐藏按钮。角色已确认仅分游客与后台管理人员，开发者和运营者各用独立账号、共用一档既定后台业务权限，不增加复杂权限配置；后台账号已确认由开发通过初始化脚本创建，凭据不写入公开仓库，不开放后台自助注册或人员管理、授权页面，既有集中运营方式和不做商家账号的边界保持；人员管理权限不替代 AI 内部服务的独立访问控制。

用户已确认游客取消权限：当前访客只能自行取消自己的商品 `PENDING_PICKUP`、餐食 `PENDING_VISIT` 和住宿 `PENDING_CONFIRMATION` 订单；住宿进入 `CONFIRMED` 后仅由运营后台处理取消。已取货、已完成和已取消均为终态，不允许再取消。Java 同时核对归属、订单类型和操作时的当前状态，不能仅依赖前端按钮；若后台已推进状态，游客的过期操作不得覆盖该结果。本期不新增退款、取消截止时间或线上取消审批流，具体接口与并发控制方式留待技术讨论。

### 2.3 社区与路线攻略

`community_post` 扩展为普通动态与路线攻略两种内容类型。动态最小字段包括 `visitor_id`、正文、标签、作者展示名、内容类型、演示标识和发布时间；路线攻略追加标题、节点顺序/摘要与地点引用。

游客可发布文字与标签动态、按标签或内容类型读取动态。没有图片上传、评论、点赞、收藏、举报或审核流。路线攻略属于同一篇社区内容；行模块只引用其卡片作为个人经验，不复制为第二套路线数据，也不标为官方路线。

### 2.4 地点与地图服务

Java 对游客端和 Python 提供地点/景点的已发布资料与来源，当前先支持水彩虚拟示意地图。固定节点使用相对坐标 `(x, y)` 与连线表示路线顺序，与真实经纬度独立保存；未知经纬度保持为空，不从原始手绘图推算。

当前没有地图授权，示意地图依据既有资料和可找到的信息制作，页面与 API 明确标注演示和非等比例，不提供精准里程/时长、实时交通/班次、实时导航或官方安全承诺。真实底图、搜索、地理编码、路径计算和导航在具备服务商访问方式、授权与可核验坐标后接入，不阻塞本机示意地图。

### 2.5 接口职责

接口按领域分组，具体字段以实现阶段的契约文档为准：

```text
游客端：
GET  /api/products                 GET /api/products/{id}
GET  /api/foods?merchantId=         GET /api/foods/{id}
GET  /api/stays                    GET /api/stays/{id}
GET  /api/places
GET  /api/posts?type=&tag=
POST /api/posts
POST /api/product-orders           GET /api/me/product-orders
POST /api/food-orders              GET /api/me/food-orders
POST /api/stay-bookings            GET /api/me/stay-bookings

运营端：
/api/admin/merchants
/api/admin/products
/api/admin/foods
/api/admin/stays 与 /api/admin/room-types
/api/admin/places
/api/admin/orders/*/status
/api/admin/knowledge-documents
```

`visitorId` 作为受校验的访客归属凭据随请求传入；响应不得返回其他访客的联系人信息、内部存储路径、密钥、签名 URL、未脱敏错误或不属于当前访客的订单。

## 3. Python LangGraph AI 服务

### 3.1 会话与图结构

2026-09-10 用户确认：同一账号跨 Web 与小程序继续规划时，AI 以 Java 提供的最新已保存行程为修改基础，须校验数据归属；首版暂不跨端同步逐条聊天记录，不要求两端共用一个 `threadId`。当前会话上下文记忆及下述持久化恢复要求保留，旧检查点不得被当作最新已保存行程或静默覆盖手动修改。AI 新方案仍先预览，用户采用后才更新业务成果；未保存候选不自动进入跨端成果。上下文衔接、并发版本与更新通知机制另行设计，本轮不改接口或检查点实现。

同一可见工作台会话重用 `threadId`。LangGraph 持久化检查点保存已确认条件、对话摘要、上一版行程和结构化工具结果；用户补充或修改条件后生成新版本，同时保留上一版供前端标识。服务重启后的恢复能力依赖持久化检查点，不得用前端假状态冒充已理解上下文。

2026-09-10 用户确认未登录也可询问乌东文化、生成并预览行程，采用“先体验，保存时再登录”。匿名会话只使用公开资料，不能读取任何账号的私人行程、草稿、订单或联系人；保存行程或草稿、提交订单、查看个人记录仍须已验证的用户身份。`threadId` 只标识对话，不能单独作为读取私人数据的授权凭据；为维持对话而保存检查点，不等于将成果保存到账号的“我的”。匿名会话保留期限、访问凭据、调用限额与登录后本次预览衔接仍待设计，不因本次确认迁移历史匿名记录或实现新的接口。

```text
输入
→ 恢复 threadId 状态
→ 固定页面动作？ ──是──→ Java 直接查询 → 卡片
                     │否
                     ▼
                  意图与条件提取
                     ▼
                  缺条件？ ──是──→ 追问卡
                     │否
                     ▼
    目录 / 知识 / 地点 / 社区路线攻略检索
                     ▼
       地图服务可用时补充路线结果；否则如实降级
                     ▼
       行程、知识、推荐或待确认订单卡片
```

固定页面动作（看商品、餐食、住宿、地点或当前访客订单）不调用模型；自然语言请求支持茶旅行程、文化知识、商品/餐食/住宿推荐、景点与路线建议。

### 3.2 工具权限与订单边界

Python 通过 Java 内部接口读取商品、餐食、住宿、地点、知识、已发布社区路线攻略和当前线程关联的订单状态。

- AI 可以为用户已选定、且字段充分的餐食和住宿生成待确认订单；页面仍须在独立确认页提交。
- 餐食提案包含 `merchantId` 与 `items: [{ foodItemId, quantity }]`，以及整单到店时间、人数与备注，不含联系人或正式订单状态；联系方式仍由用户在确认页填写。每份提案只对应一家餐馆，跨店需求分别组织为提案并分别由用户确认。提案进入确认页后仍由 Java 重新核对归属、上架状态和模拟金额。
- 住宿提案采用 `checkInDate`、`checkOutDate`、`roomCount`、`peopleCount`，下一阶段与 Java API、Web/小程序严格解析器同步升级协议版本，不只给现有 `cardVersion=2.0` 加键；提案保存方式仍待单独锁定。
- 上述协议升级同时覆盖餐食的多明细结构，不修改现行已冻结协议来冒充新结构已经可用。
- 商品由用户在详情页选择数量并自行下单；AI 只推荐和跳转，不创建商品订单。
- Python 无权创建正式订单、修改订单状态、写入商家/商品/餐食/住宿/地点资料或发布社区动态。
- AI 不能访问游客间的订单、联系人或非公开资料。

### 3.3 结构化响应、地图与降级

响应卡固定为行程、服务推荐、知识回答、追问、待确认订单和错误。卡片包含公开标题、摘要、明确演示提示、真实服务/地点标识和可公开来源标题；不存在可靠 `serviceId`、地点标识或来源时，不显示对应详情、下单或来源动作。

地图服务商配置有效时，AI 可将路线工具的结果整理成路线卡；当前无授权时，基于地点和社区路线攻略组织水彩示意地图的节点顺序及演示/个人经验建议，不能声称有精准里程/时长、实时导航、班次或道路状态。

### 3.4 脱敏运行摘要

Java 后台展示的 AI 摘要仅含会话标识、节点名、工具类别、来源标题、耗时和最终状态。不得保存或展示提示词、原始思维链、联系人、访问令牌、密钥、内部 URL、SQL、完整工具参数或未处理异常。

商品、餐厅/菜品、住宿/房型、景点与出行 Word 资料已经提供并完成结构化审读，属于开发前期的原始数据准备，不属于游客或商家的在线导入功能。

## 5. 实施顺序与进度检查

实现按依赖推进，而非按固定时长删减：

1. Java 迁移、领域模型、目录与匿名访客归属；
2. 三类订单、状态机、游客确认与后台处理；
3. 社区动态/路线攻略、地点资料与后台维护；

每约十小时只报告已完成、进行中、风险和外部依赖，不把后续项从范围中删除。地图服务商及已核验坐标/资料仍是唯一会影响真实地图与路线结果的外部前置条件。
