## 2. 视觉方向

### 2.1 像一本在乌东慢慢写下的旅行手账

使用温暖的浅纸色、透明叠染的青绿与湖蓝，少量杏橙和靛青点出人的生活。照片保持真实的山色和肤色，不统一染成褐色。插画提供纸面的层次与情绪，照片承担真实地点与人物的证据。

| 角色 | 颜色 | 用途 |
| --- | --- | --- |
| 暖纸底 | `#FAF7EF` | 页面、卷轴留白、内容纸页 |
| 墨青 | `#294C50` | 正文、标题、重要标签 |
| 茶青 | `#397F7A` | 主操作、链接与可交互线索 |
| 淡玉 | `#A9C8AD` | 茶叶、水彩背景与轻边界 |
| 湖蓝 | `#B7D5DF` | 溪流、山色与章节过渡 |
| 杏橙 | `#C98C63` | 手账章号、小面积人文强调 |

标题延续有书写气质的中文衬线字；按钮、字段与长正文使用清楚的中文无衬线。手写风格只用于短标题或注记，不用于联系人、金额和状态。浅绿浅蓝不直接作为小字号正文颜色。

页面留白承担“宁静”，插画细节承担“丰富”。不把每张卡片都做成复杂手绘边框，不添加满屏粒子、反复弹跳或永久强视差。后台保持清晰的表格与工具布局。

### 2.2 卷轴主画

采用新生成的整幅水彩插画：山林、茶、采茶人物、染布、溪流、木楼、桥、茶器和银饰小物相互关联。中央上部留白放网站标题与“点击这里”。两片卷面使用同一幅画的对应半幅，避免左右各画一套导致接缝不连续。

画面只是一幅受乌东资料启发的概念插画，不是实景、地理地图、服饰考据或当地传统卷轴的复原。人物是概念人物；具体纹样不解释为祭祀符号或传统寓意。避免泛贵州峰林、侗族鼓楼、夸张银角冠和千户灯海替代乌东。

首次进入必须手动点击才打开；当前会话打开后不再强制重复。保留清晰的重看入口便于答辩演示。不开场加雾遮景。图片失败时文字与开卷按钮仍可操作，不让艺术资源成为进入网站的前提。

### 2.3 五景与单屏探景

保留“山、水、寨、茶、人”五联实景、照片来源与焦点位置。“寨”继续使用用户确认的带“乌东苗寨”文字照片；茶联保留采茶照。画面外围变成轻薄的纸面裱画关系，两侧留白，以软光影形成深度，不用厚重深褐框。

点击照片仍打开独立探景层：一张大图、一段短章、一个下一步操作。普通桌面窗口内保持一屏，不用巨大图片撑出纵向滚动。窄屏/低高度下重新分配图文比例；关闭按钮始终可见，支持键盘关闭。此单屏约束针对五景探景层，不强迫商品长介绍、订单页和社区全文也塞进一屏。

### 2.4 下滑、溪流与向导

五景之后的过渡使用远、中、近三层浅雾，进入叙事时移动并散开；不能出现盖住文字的大白矩形。雾属于章节过渡，不覆盖开卷前的全貌。

保留贯穿三段故事的溪流线与水纹。两岸配合新的淡水彩溪岸画、照片与注记，让溪流成为串联内容的动线。装饰线不是地图，不提供准确距离或步行时长。

三段故事分别是沿溪入寨、俯看村谷、人在寨中。游客文案改为对场景的自然描述；原来的“这是页面叙事名称”“不使用标签化人物描述”等内部设计说明退出产品界面，资料风险留在开发文档和适当的来源说明中。

向导区从整片深绿改为纸白与浅溪蓝的手账工作台。叶子仍作为同行提示，进入向导附近后降低存在感；按钮与叶片交互仍有轻回弹、水纹回应。所有动效遵守减少动态效果设置，不牺牲可操作性。

## 3. 五模块布局与本轮边界

目标一级导航仍为“贵州乌东｜逛乌东｜乌东向导｜预约 / 我的｜运营后台”。本轮先改现有页面的视觉，不借换肤顺手重做路由；总览与新模块入口归位在后续业务任务中落实。

| 模块 | 页面重点 | 资料怎样进入页面 | 交易或功能边界 |
| --- | --- | --- | --- |
| 商品 | 茶与伴手礼、苗绣、银饰、染织；图片、短故事、规格和取货 | 雷山银球茶、苗绣包、蜡染布艺等作为目录候选；产地与商家逐项标记 | 现场自提；无配送/支付，模拟业务值必须标明，不能冒充真实库存 |
| 食 | 按店认识风味，再从菜单多选菜品、饮品或套餐 | 商家信息与其菜品/饮品/套餐关联；套餐可以作为独立餐食项 | 店内选餐篮汇总多道菜及份数，整单确认到店时间、人数与联系人；不跨店合单，不做外卖 |
| 住 | 民宿主体与房型分层，先环境再房间 | 民宿照片不自动充当房型照片；原始容量/参考价格与模拟值分列 | 入住/离店日期、房间数、人数预约，仍后台确认；仅按明确模拟口径演示计价，无实时房态、动态价格或库存锁定 |
| 行 | 水彩虚拟示意地图、地点、抵达信息、漫游顺序与社区攻略 | 风雨桥、水碾房、芦笙场、诸野书店、大山里的美术馆等资料 | 独立页面，固定相对节点与连线表达顺序，非等比例；真实地图后续接入，无门票/交通订单 |
| 社区 | 文字与标签发布、普通动态与路线攻略 | 编辑整理的文化内容与游客动态区分身份和来源 | 不自动增加图片上传、点赞、评论或审核 |

“逛乌东”总览提供五张主题卡、一条茶旅灵感和向导入口，不复刻首页长卷。Web 列表沿用侧栏筛选与卡片；小程序用单列与横滑筛选，首页不照搬全屏长卷。

餐食的店铺分组可以复用 `merchant → food_item`，不急于新增第二套餐饮子系统。同一家民宿有住宿与餐饮时，在核对同一经营主体后复用商家；房型和菜品仍是不同资源。

同一经营者的不同餐馆也不能仅凭同名或共同经营者合并店铺记录。菜单与到店订单以具体店铺的 `merchantId` 区分，后台按店维护和处理；这一归属规则不扩展为商家登录或多租户权限系统。

## 4. Word 资料已经提供了什么

完整提取记录包含 755 个正文段落（508 个有文字）、14 个 OOXML 表格、228 个媒体文件、284 次图片引用。住宿房型和景点距离还有内嵌表格截图，不能仅靠提取文字读取。

本次结构化整理得到 10 家住宿、33 条房型候选，12 家餐饮条目、100 条菜品或饮品记录和 14 个套餐。它们是原文记录数量，不是对当前乌东营业商户数量的认证。商品部分大多是跨地区品类与市场参考价，不是已经具备库存的乌东 SKU。

最有价值的内容组织方式是“地方知识 → 可浏览的空间或服务 → 游客明确选择 → 确认提交”。例如：水碾房解释山水与生产的关系；诸野书店和美术馆承接当代村寨生活；茶、餐食、住宿承接停留决策。不能只把整份 Word 拆成一墙商品卡。

### 4.1 四类内容状态

- 本地资料候选：文档明确写乌东名称/地址，仍保留来源与核验状态。
- 区域文化知识：雷山、台江、西江等背景资料，只能按其真实范围表述。
- 市场参考：电商价格、批发价格、外地采购渠道，用于选品研究，不包装为本村在售。
- 冲突或敏感内容：不确定房型、图片复用、未经核实的文化数量/工艺/营养宣称，进入内部待核对清单。

1. 云山初见的房型截图 `image54` 中，大床/双床名称与床型文字不一致；不能自动改成某一种并当成确定容量。

## 5. 确认与可信表达

用户已确认下面的草稿与正式订单分离体验；具体存储与接口实现留待技术讨论锁定，不据此认定相关代码已经实现：

1. **AI 提案 / 草稿**：向导整理出的订餐或住宿建议，保存为与正式订单分开的草稿，没有正式订单号；用户离开后可以在“我的”中找到并继续修改，确认提交才创建正式订单。保存触发时机、提交后的草稿处理和技术存储方案留待后续讨论；当前仍沿用本机匿名访客，不据此承诺 Web 与小程序自动跨端同步。
2. **游客提交**：游客在确认页核对字段后，由 Java 创建商品订单、到店订单或住宿预约。
3. **住宿方确认**：已经提交的住宿预约，后续从“待确认”推进到“已确认”。它不是第二次让 AI 替游客确认。

商品初态待取货；餐食初态待到店；住宿初态待确认。模拟流程也必须使用真实服务端返回，不在提交失败后伪造成功。

餐食已确认采用“一家餐馆、一张订单、多条菜品明细”。游客在店内菜单选择菜品、饮品或套餐及正整数份数，进入整单确认页核对模拟单价、明细金额、合计、到店时间、人数与联系方式。Java 只接收该店的有效上架餐食，按服务端明确单位的模拟单价计算，主单和明细一次保存并保留价格快照；混店请求整单拒绝，不部分下单。我的订单和后台显示同一张主单及其明细，菜单改价不改写历史订单；仍无支付、配送、退款或逐菜履约状态。

API 和 AI 餐食提案同步采用 `merchantId`、`items: [{ foodItemId, quantity }]` 及整单到店字段，下一阶段与住宿字段一并升级 Java API 和两端严格解析器，不只给现有 `cardVersion=2.0` 加键。AI 只能提供同店选餐提案，用户仍须独立确认提交；提案保存方式尚未定案。

原始参考价格、未知价格和模拟价格应区别展示：“参考价格，待商家确认”不能写成“今日特价”；原始缺失值不显示数字零，允许另填带明确口径的本机模拟价格。模拟容量等也与原始参考分列，不当作真实商家事实。公共空间的到访时间与书店、餐厅的营业时间不能混用。

住宿字段为 `checkInDate`、`checkOutDate`、`roomCount`、`peopleCount`；离店晚于入住，房间数和人数为正整数，夜数由日期计算。仅在明确模拟计价单位与口径时展示演示金额，例如模拟价明确为元/间/晚时按夜数与房间数计算；不把单位缺失的原始参考价用于多晚计算，不承诺真实金额。下一阶段 Java API、AI 提案、Web/小程序严格解析器须同步升级协议版本，不能只向现有 `cardVersion=2.0` 加键；AI 提案存储方式仍未定案。

当前没有地图授权，先依据既有资料和可找到的信息制作水彩虚拟示意地图。固定节点使用相对坐标 `(x, y)` 与连线，独立于真实经纬度；地图清楚标明“虚拟示意地图，非等比例”，只表达路线顺序，不显示精准里程/时长、虚构班次或实时导航声称，不从手绘图推算经纬度。地点列表作为辅助，真实地图后续再接入。

## 6. PDF 扩展能力的讨论区

PDF 提及照片投稿、评论点赞、可订日期、线路/门票和后台角色权限；其中超出既定范围的部分，本轮不自动加入，也不把示例日历当真实房态能力。商家登录、真实支付与退款属于既定范围的其他排除项，并非本次已确认从 PDF 采纳的需求。

推荐先完成三类业务闭环、资料可追溯、独立行页与社区攻略共享。若之后增加社区图片投稿，还要补文件大小/类型限制、存储、删除与审核，不能只做一个上传按钮。住宿起止日期与房间数已确认纳入下一阶段，按第 5 节同时落实字段、校验、夜数和模拟计价语义，不能只修改日期控件。

## 7. 后续需要用户支持的内容

本机资料已足够继续整理和造演示样例。民宿容量、餐食价格、商品规格与取货点等缺项可由开发者补充模拟值，清楚标记后打通本机闭环，无需先等待用户逐项核验。真实经营样本后续用于逐条核验及真实可售准备，不能把演示样例当成当前商家承诺。

后续仍需分别落实照片使用范围、真实地图服务商/授权/可核验坐标，以及云 Embedding 的端点、模型名、向量维度和访问配置。当前没有地图授权已明确，先行水彩示意地图不等待这些真实地图条件。模拟数据授权不等于素材权利许可或公开可售授权，不伪造真人联系方式或权利许可。密钥仅在本机配置，不粘贴到文档或仓库。

这些信息不阻塞本机模拟数据、示意地图与业务演示开发；它们决定后续哪些内容可以从“参考/演示”升级为真实服务或公开使用。
