# 贵州乌东五模块前端设计规格

**状态：** 用户已确认（2026-09-09）；本轮补充决策已确认，对应实现尚未开始。
**范围：** 在已确认的沉浸首页与乌东向导基础上，重定“逛乌东”、商品、食、住、行、社区、确认/我的订单与运营后台的页面职责和布局。
**不包含：** 本规格不授权代码、接口、数据库、地图 SDK、真实支付、测试或部署变更。

## 1. 已确认的信息架构

产品对外名称统一为“贵州乌东”。顶部一级入口采用精简结构：

```text
贵州乌东｜逛乌东｜乌东向导｜预约 / 我的｜运营后台
```

“逛乌东”是独立总览页，而非下拉菜单或常驻二级导航。首页在已确认的沉浸叙事之后，保留五个快捷入口；顶部“逛乌东”和这五个入口都进入总览或对应模块。

```text
逛乌东
├── 商品
├── 食
├── 住
├── 行
└── 社区
```

旧的“游乌东”“服务详情”“寨里”不再作为独立一级模块：原有内容分别迁移为五模块内的列表/详情页、社区动态和路线攻略。首页、乌东向导、预约、我的订单与运营后台保留。

## 2. 总体视觉与端侧规则

- 首页和乌东向导继续遵循已批准的“山静 · 人暖”、开卷、五联实景、沿溪叙事与 AI 工作台规格；本设计不重新定义它们。
- 逛乌东及五模块从首页叙事过渡到清晰、可操作的工具页面：湿山深绿、雾纸白、溪石青与火塘铜沿用既有色彩令牌，但不复制卷轴、雾效或五联动画。
- 未核验的地点、价格、库存、图片、路线、开放时间、班次与用户分享均须明确标注“演示数据”“个人经验”或“以服务方/实时数据为准”。
- 桌面端列表页采用筛选侧栏与卡片网格；小程序采用单列卡片、横滑筛选或底部筛选层，以及一个固定的主操作按钮。
- 不新增真实支付、正式登录、外卖配送、图片上传、评论、点赞、收藏、社区审核或生产账户体系。

## 3. 逛乌东总览

### 3.1 页面职责

总览页只帮助用户选择体验，不承担首页叙事、完整商品列表或订单处理。页面顺序固定为：

```text
顶部导航
→ 茶旅引导语与“今天，想怎么逛乌东？”
→ 商品 / 食 / 住 / 行 / 社区五张主题卡
→ 一条茶旅推荐
→ 继续上次行程或进入乌东向导
```

五张卡的语义为：商品“带走乌东”、食“吃一口乌东”、住“住进山里”、行“抵达与游览”、社区“看看寨里”。总览页的推荐内容必须是演示数据，且不能宣称服务可订、路线已开放或图片已授权。

### 3.2 小程序

“逛乌东”作为主栏页面，五张卡以 2×2 加底部全宽社区卡呈现；不复刻 Web 首页长卷。小程序底栏沿用已确认的首页、逛乌东、向导、寨里/社区、我的语义，其中“寨里”对用户显示为“社区”。

## 4. 商品、食、住

三类页面共用“列表 → 详情 → 提交前核对 → 我的订单”的骨架，但不共用交易字段或状态。

| 模块 | 列表筛选与卡片 | 详情页唯一确认字段 | 主操作 | 履约与订单状态 |
| --- | --- | --- | --- | --- |
| 商品 | 茶与伴手礼、苗绣文创、价格区间 | 数量、现场取货点、联系方式 | 立即下单 | 现场自提：待取货 / 已取货 / 已取消 |
| 食 | 按店浏览，再筛选茶点、正餐、体验、到店时段、人数 | 店铺、同店菜品/饮品/套餐及份数、到店时间、人数、联系方式 | 核对选餐并提交到店订单 | 到店消费：待到店 / 已完成 / 已取消 |
| 住 | 入住/离店日期、房间数、人数、房型 | `checkInDate`、`checkOutDate`、`roomCount`、`peopleCount`、联系方式 | 提交住宿预约 | 住宿：待确认 / 已确认 / 已完成 / 已取消 |

详情页采用左侧实景/商品图与短故事、右侧关键信息和唯一主操作的布局。商品、餐食和住宿都必须展示演示数据提示；不承诺产地、库存、餐位、房态、开放时间或价格。小程序详情页以单列呈现，在底部固定对应的唯一主操作。

餐食从店铺介绍进入该店菜单，允许多选菜品、饮品或套餐并增减份数；Web 以侧栏选餐摘要、小程序以底部选餐栏汇总，同店一次确认成为一张到店订单。选餐区始终显示当前店名，不能将其他店铺的菜品混入该单；不做跨店购物车。独立确认页列出店名、各项份数、模拟单价与行金额、模拟合计，以及整单共用的到店时间、人数、联系方式。我的订单按主单显示店名和摘要，详情展示全部菜品明细；不为每道菜分别生成订单或状态。

商品只支持现场自提；食仅表示到店餐食或茶点体验，不做配送；住采用后台确认预约，不做真实支付、实时房态、动态价格或库存锁定。住宿离店日期必须晚于入住日期，房间数和人数为正整数，夜数由日期计算；仅在明确模拟计价单位和口径时展示演示金额，不承诺真实价格。

## 5. 行：地图与路线规划

“行”页面当前先制作水彩风格虚拟示意地图，依据既有资料和可找到的信息组织地点与路线顺序。当前没有地图授权；真实地图服务商、可核验坐标、地理编码、路径计算、实时交通/班次和导航跳转后续再接入。

桌面端固定为左侧规划面板、右侧地图主画布：

```text
出发地 / 出行日期 / 人数
→ 生成路线
→ 水彩示意地图的固定节点与连线
→ 抵达建议、村内游览顺序、茶旅与餐食/住宿衔接的路线卡
```

小程序固定为“表单 → 全宽示意地图 → 底部路线卡”。地图清楚显示“虚拟示意地图，非等比例”，节点使用固定相对坐标 `(x, y)` 与连线，独立于真实经纬度，不从图中反推地理坐标。路线只表达游览顺序和衔接，不显示精准里程/时长、班次或实时导航声称；地点列表作为辅助保留，不以地图未授权为由只留空白或列表。

“行”页在地图与路线卡之后增加“借鉴大家的路线攻略”区块，展示社区中标为路线攻略的卡片；点击进入该社区动态。攻略只提供行程灵感，须提示以实时地图、服务方和现场情况为准。

## 6. 社区与路线攻略

社区采用轻量模式：演示身份可发布文字和标签；用户可浏览按最新排序的动态流。没有图片上传、评论、点赞、收藏、举报或审核工作流。

页面组成：

```text
发布框（正文 + 茶旅/苗寨生活/路线攻略标签）
→ 分类切换（全部 / 茶旅 / 村寨生活 / 路线攻略）
→ 动态流
→ 热门路线与个人经验说明
```

路线攻略是社区的内容类型，不创建另一份路线数据。路线攻略卡必须含标题、节点顺序、标签和“个人经验 / 演示数据”标识；“行”模块只引用同一篇内容。

## 7. 确认、我的订单与后台

### 7.1 游客端

三个提交页均先展示服务/商品、对应字段、联系方式与演示提示，再由用户主动确认。确认成功后进入我的订单。我的订单按“全部、商品、食、住、行程”筛选；每张卡显示名称、关键字段、状态和演示标识。订单详情解释状态，但不提供支付、退款或配送追踪。

用户已确认：“我的”增加可找回的 AI 订餐/住宿草稿，与正式订单区分展示；离开后可继续修改，经确认页主动提交才生成订单。草稿不是“待到店”订单或“待商家确认”的住宿预约，不冒充商家已经收到申请。此确认不包含正式登录或 Web/小程序自动跨端同步；具体布局、保存触发与提交后处理规则继续讨论。

### 7.2 运营后台

后台保持工具型布局，不使用首页沉浸动效。顶部栏目为：订单、商品/餐食/住宿、知识与攻略、AI 运行摘要。首页摘要展示待取货商品、待到店餐食、待确认住宿与 AI 运行摘要。订单处理只能按第 4 节规定的类型状态流转。

餐食管理支持按店维护菜单和筛选到店订单；订单详情显示该店整单菜品、份数及金额快照。店铺独立是资料和订单归属独立，本期仍由集中运营后台处理，不新增商家登录或商家权限体系。

后台不新增社区评论审核或真实支付管理；路线攻略作为社区内容展示，不能被标为官方路线。

## 8. 前后端衔接边界

- 前端后续需要三类订单、三个独立状态机、商品/餐食/住宿目录与详情、社区文字动态和路线攻略类型。
- 水彩虚拟示意地图不依赖真实地图授权；真实地图能力待服务商、API 访问方式、地点坐标与授权齐备后接入，不能把示意节点当实时定位。
- 餐食的 `merchantId`、`items: [{ foodItemId, quantity }]` 和住宿四字段须在下一阶段同步到 Java API、AI 提案和两端严格解析器并升级协议版本；不能直接给现有 `cardVersion=2.0` 加键。餐食模拟合计以 Java 校验、计算后的结果为准，不把前端选餐摘要当成已提交订单。
- 乌东向导可跳转到商品、食、住、行或预约，但不得绕开确认页直接创建正式订单。
- 所有 AI、社区和地图的演示内容应与真实能力区分显示；不得暴露内部提示、密钥、绝对路径、内部 ID 或未脱敏执行信息。

## 9. 规格自检

- 示意地图已确认纳入下一阶段；地图服务商、坐标和实时数据仅约束后续真实地图接入，不阻塞本机示意展示。
- 订单路径一致：商品自提、餐食到店、住宿预约均经过确认页与我的订单，并在后台按类型处理。
- 社区与行的路线攻略共享一份内容，不新增重复数据源或第二套行程系统。
- 范围受控：没有支付、配送、实时房态、社交互动、图片上传或地图服务接入实现。

## 本轮用户确认补充（2026-09-09）

- 缺少的价格、容量等可由开发者补为本机模拟样例，无需先等待用户核验；原始参考值与模拟值分列并注明口径。演示不等于真实商家报价、容量、库存或公开可售，不伪造真人联系方式和权利许可。
- 当前没有地图授权，先依据既有资料和可找到的信息制作水彩虚拟示意地图；固定相对节点和连线只表达路线关系，非等比例，不提供精准里程/时长或实时导航。真实地图后续接入，本轮不开始联网生成地图。
- 住宿确认增加离店日期和房间数，采用 `checkInDate`、`checkOutDate`、`roomCount`、`peopleCount`；仍后台确认，不增加实时房态、动态价格或库存锁定，三类订单状态不变。
- 餐食确认同店多菜合单，使用店内选餐栏、整单确认页和按店管理的后台；不同店铺分别下单，不新增跨店购物车或商家账号。
- 以上是已确认设计补充，尚未开始实现；AI 提案存储方式及其他未定项未因本轮补充而定案。
